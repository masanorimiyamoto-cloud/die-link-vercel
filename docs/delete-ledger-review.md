対象：`636ef4a` 時点のスマホ・API・回帰テスト、および削除連携の引継ぎ資料。

削除台帳を受注より先に保存する仕組みは実装され、Excel登録済みの受注にも削除対象が広がっている。`node tools/process-regression.cjs` は **53/53成功**。`memory/delete-ledger.md` には、事務所PCで受注が退避・削除され、Excel反映済みになった実地確認の記載がある。

一方、追加の全面モック検証では、並行処理・応答消失に対する不足を確認した。優先度は、実際に行った再現条件に対して付けている。実運用で発生した障害を報告するものではない。

## 1. 工程記録が入った受注を、削除処理が消してしまう（P1）

対象：`api/_process.js:798`、`:817`、`:843`、`:851`。関連：工程完了処理 `complete` の419行付近。

受注の取得・削除可否の判定から、台帳作成・実際のDELETEまでに時間差がある。その間の別端末からの工程記録や伝票更新に対して、削除処理との排他がない。

再現手順：

1. 工程記録がないExcel登録済み受注の削除を開始する。
2. 初回の受注取得後、削除台帳のPOSTが完了するタイミングで、偽Airtable上の受注へ「機械貼完了」とその記録を追加する。
3. 削除処理を続行する。

実際のAPI関数を偽Airtableへ接続した結果：

```json
{
  "workRecorded": true,
  "orderExists": false,
  "deleteSuccess": true,
  "snapshotContainsNewRecord": false
}
```

「工程の記録・伝票がある受注は消さない」という条件を、並行操作の場合には守れていない。削除前の内容も初回取得時のものなので、後から入った記録は削除台帳のスナップショットに残らない。

必要な修正：受注単位で削除と他の更新を調整する仕組みを導入し、削除直前にも条件を検証する。スマホの別端末・別サーバーインスタンス・Excel同期などの書込経路を対象にする。画面内の `runOp` や、サーバー内の一時的なMapだけでは端末間の競合は防げない。直前の再取得だけでも競合の隙間は残るため、それだけで完了としない。

追加確認：工程記録・伝票更新が先に確定した場合は削除を止める。削除が先に確定した場合は、後続の工程記録を成功と返さない。

## 2. 削除結果が不明なのに「受注は残っている」と確定する（P1）

対象：`api/_process.js:852`〜`:858`、`public/process.html:2025`〜`:2029`。

DELETEの応答が失われ、続けて行うGETも失敗すると、サーバーは `still = true` のまま台帳を「要確認」にして「受注は残っている」と記録する。実際にDELETEが反映されたかどうかは、この時点では分からない。

再現手順：DELETE自体は偽Airtableに反映させたうえで通信例外を返し、確認用GETにも通信例外を返す。

結果：

```json
{
  "orderExists": false,
  "ledgerState": "要確認",
  "response": { "ok": false, "error": "消せませんでした（SIMULATED_RESPONSE_LOST）" }
}
```

処理メモには「受注は残っている」と書かれた。さらに画面は通常のエラーとして `S.delPending` を消し、同じ要求IDによる結果確認の導線を失う。

引継ぎ資料どおりExcel側が「受付済」「Airtable削除済」だけを処理する場合、このケースは自動的な反映対象から外れる。実際のExcel同期の「要確認」の扱いは、このPCではコードを参照できないため未確認。

必要な修正：

- 受注が残っていると確認できた場合と、確認そのものに失敗した場合を分ける。
- 結果不明の場合は、台帳に削除意図を残したまま、後から照合できる状態・メッセージにする。
- APIは結果不明を画面へ伝え、画面は元の要求IDを保持して照合する。
- Excel同期側も、通信失敗を「存在しない」または「存在する」と断定しない。

## 3. 同じ削除要求IDの台帳が重複する（P2）

対象：`api/_process.js:778`〜`:782`、`:831`〜`:843`、共通 `airtable` 関数の151行付近。

現在の「検索して、なければPOST」は同時実行時の一意性を保証しない。さらに、台帳POSTが保存された後に503が返った場合、共通通信関数がPOSTを再送し、2行作成する。

追加検証結果：

| 条件 | 結果 |
|---|---|
| 同じ要求IDを2つ同時に送信 | 両方成功、台帳2行 |
| 台帳POSTは保存済み、応答だけ503 | 台帳2行。「受付済」と「Airtable削除済」が並存 |

既存のL1テストは、既に台帳がある場合の順次再送を検証している。同時実行と、保存後の異常応答は検証していない。

主欄を削除要求IDにしても、Airtableは主欄の値の一意性を要求しない。[Airtable公式資料](https://support.airtable.com/articles/8978269981-the-primary-field-in-airtable)もこの点を説明している。

必要な修正：要求IDによる重複防止を同時実行・応答消失に対応させる。非冪等な台帳POSTへ共通の無条件再送を適用しない。既に重複した場合も、`ledgerByReq` で先頭1行だけを採用せず、不整合を検出して処理できるようにする。

Excel側も重複要求で別の行を消さず、同じ要求ID・受注IDの適用済み記録を確認する。[AWSの設計資料](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)にも、重複配信を前提に受信側を再実行可能にする考え方がある。本実装がDBトランザクションによる厳密なoutboxを実現しているという意味ではない。

## 4. Excel反映済みを、APIがAirtable削除済へ戻す（P2）

対象：`api/_process.js:811`、`:863`。

引継ぎ資料では、Excel同期は「受付済」でも対象受注が404なら処理できる。このため、次の順序が成立する。

1. APIがAirtableの受注を削除する。
2. APIの台帳更新より先に、Excel同期が受注不存在を確認して退避・削除・保存し、台帳を「Excel反映済」にする。
3. APIが台帳を無条件に「Airtable削除済」へ更新する。

Excel同期による状態更新を偽Airtable上で挟み、実際のAPI関数を続行した結果：

```json
{
  "ledgerState": "Airtable削除済",
  "excelAt": "2026-11-03T07:01:00.000Z",
  "response": "Airtable削除済"
}
```

反映日時があるのに、表示と状態は反映待ちに戻る。Excel同期が再処理すれば回復する可能性はあるが、その挙動と退避の重複防止はExcel側のコード確認が必要。

必要な修正：状態が後退しないよう、スマホ側とExcel側の更新責任を分ける。例えば、Airtable削除確認とExcel保存確認を独立した項目にし、Excel保存確認がある場合は完了として扱う。更新直前に状態を読むだけでは、その読込後の競合までは防げない。

## 5. Excel側で確認が必要な事項

`Z:\Airtable\delete_ledger.py` はこのPCから参照できなかった。以下は**未確認項目であり、未実装と断定していない**。

1. 削除対象は正しいブック・受注表のRecordID完全一致だけか。重複行は削除せず停止するか。
2. 退避・削除・適用済みの記録が、同じExcel保存で確定するか。保存に失敗したら反映済みにしないか。
3. 保存失敗後の再実行で、未保存のExcelメモリー上に退避行があるだけで反映済みにしていないか。保存成功を再確認できるか。
4. Excel→Airtable送信と、Airtable→Excel新規取込の両方が削除台帳を参照するか。台帳が読めなかったとき、空の除外一覧で通常同期を続けていないか。
5. 復活防止用のRecordID取得で全ページを読み、「Excel反映済」も含めた必要な履歴を維持しているか。スマホ表示用の最近30件だけでは不足する。
6. 台帳を読んだ後に新しい削除が受け付けられる競合、取込済みデータが削除処理後に書き込まれる競合にも対応しているか。
7. 同期の二重起動と、同じ削除要求の再処理が安全か。台帳反映だけ失敗した場合に再退避・誤削除しないか。

Excel側のソースを確認できるまでは、正常系の実地確認の記録だけでこれらの条件まで満たしたとは判断できない。
