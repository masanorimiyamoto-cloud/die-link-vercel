# 受注の削除台帳と Excel 同期（引き継ぎ）

2026-11-03。スマホ（die-link-vercel）側は実装済み・デプロイ済み。**Excel 同期側（事務所 PC）は未実装**。このメモは Excel にアクセスするコードを持つ PC で続きをするためのもの。

## 1. 考え方

削除の意思は受注（TableJuchu）とは別の **削除台帳（TableDeleteLedger）** に残す。Excel 同期は、この台帳に明示された受注だけを削除対象にする。品番（Book / WorkCord）では判定せず、**受注RecordID が一致する行だけ**を扱う。

## 2. 台帳のテーブル

Base `appwAnJP9OOZ3MVF5`、テーブル `TableDeleteLedger`（`tblpQzjyEoYQO9Ala`）。1行 = 削除1回。行は履歴として残し、消さない。

| 欄 | 型 | 書く側 | 内容 |
|---|---|---|---|
| 削除要求ID | 1行テキスト（主欄） | スマホ | `del-<uuid>`。送り直しでも同じ値。同じ値の行は作らない |
| 受注RecordID | 1行テキスト | スマホ | 消した受注の `rec...`。**Excel の対象行はこれだけで決める** |
| 状態 | 単一選択 | 両方 | 受付済／Airtable削除済／Excel反映済／要確認 |
| Excel登録前 | チェック | スマホ | 削除時に Add_from_Airtable が ON だった |
| Book / WorkCord / ItemName / NAmount / Ndate | 各種 | スマホ | 確認・復旧用（WorkCord は文字列） |
| 削除内容 | 長文 | スマホ | 削除前の主な欄の JSON |
| 削除理由・操作者・社員番号・受付日時 | 各種 | スマホ | 誰がいつ何のために消したか |
| Airtable削除日時 | 日時 | スマホ | 受注を消した日時 |
| Excel反映日時 | 日時 | **Excel 同期** | Excel の保存に成功した日時 |
| 処理メモ | 長文 | 両方 | `YYYY-MM-DD HH:MM 内容` を1行ずつ追記 |

## 3. スマホ側の処理順（実装済み：`api/_process.js` の `deleteOrder`）

1. 削除を確認し、理由（任意）を入れる。画面が削除要求IDを作る。
2. 台帳に「受付済」で1行書く。**書けなければ受注は消さない。**
3. Airtable の受注を消し、台帳を「Airtable削除済」にする。
4. 途中で止まった場合：
   - 受注を消せなかったときは、台帳を「要確認」にし、処理メモに理由を書く（受注は残っている）。
   - 受注を消した後に台帳を更新できなかったときは、台帳が「受付済」のまま残る。**Excel 同期はこの場合も削除済として扱う**（下の 4-1）。
   - 送り直し（同じ削除要求ID）では、台帳から続きを処理する。受注を二度消したり、台帳を2行にしたりはしない。

今のところ、スマホで消せるのは **Excel にまだ入っていない受注（Add_from_Airtable が ON）で、工程の記録・伝票が無いもの**だけ。Excel 登録済の受注の削除は、Excel 同期側ができてから解禁する（6 章）。

画面には「削除した受注（Excel 反映の状況）」の欄があり、台帳の最近 30 件を「Excel 反映待ち／Excel 反映済み／要確認」で表示する。

## 4. Excel 同期側でやること（未実装）

### 4-1. 台帳を読んで Excel の行を消す

1. 台帳から、状態が「Airtable削除済」または「受付済」の行を読む。
2. 状態が「受付済」の行は、TableJuchu の `受注RecordID` を GET して確かめる。
   - 404（無い）なら削除済として扱う。台帳を「Airtable削除済」に進めてもよい。
   - まだ有るなら、スマホ側の処理中か失敗のため**触らない**。受付日時から 1 時間以上たっても有るときは「要確認」にする。
3. S96.5 で、RecordID の列が `受注RecordID` と一致する行を探す。
   - **1行**なら、その行を退避用シートへ写す（削除要求ID・日時も添える）。その後で行を削除し、ブックを保存する。
   - **0行**で、`Excel登録前` が ON なら正常。台帳を「Excel反映済」にし、処理メモに「Excel に行なし（登録前）」と書く。
   - **0行**で、退避用シートに同じ削除要求IDがあるなら、前回に消したが台帳を更新できなかったケース。「Excel反映済」にする。
   - **0行**でそれ以外なら「要確認」にする。
   - **2行以上**なら、何も消さずに「要確認」にする。
4. **ブックの保存が成功してから**、台帳を「Excel反映済」にし、Excel反映日時を書く。保存に失敗したら台帳は変えない（次回やり直す）。

同じ台帳の行を何度処理しても、別の行を消さないこと（RecordID の完全一致だけで判定し、退避用シートで済みかどうかを確かめる）。

### 4-2. 復活の防止（必須）

台帳に載った受注RecordID（**状態を問わず**）は、次の処理から外す。

- Excel → Airtable の送信。消した受注を作り直したり、更新したりしない。
- `Airtable_Fetch.py` が Add_from_Airtable の受注を Excel に足す処理。消える直前に読んだ受注を足さない。

台帳の RecordID の一覧は、実行のたびに1回まとめて読めば足りる。

### 4-3. 取り込みとの競合

スマホで消す直前に `Airtable_Fetch.py` が行を足していた場合、`Excel登録前` は ON のままでも Excel に行がある。4-1 の手順で1行見つかれば、通常どおり退避して消す。

## 5. 確認用

- 台帳の行は Airtable の画面で見られる。「要確認」の行は処理メモの最後の行に理由がある。
- スマホ側のテスト：`node tools/process-regression.cjs` の L1。偽の Airtable を相手に、処理の順番・送り直し・台帳の更新失敗を確かめる。
- PAT は同じ Base のため、既存のもので台帳を読み書きできるはず（テーブル単位の制限をしていなければ）。

## 6. Excel 側ができた後

- Excel 登録済の受注をスマホから消せるようにするかどうかを決める。その場合は `deleteOrder` の `addPending` の条件を外す。`renderDelete` の表示条件も合わせて直す。
- 伝票・工程の記録がある受注は、引き続き消さない。
