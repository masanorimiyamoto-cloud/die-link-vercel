# Claude Codeへの実装指示：作業共有画面の改善（コード照合済み改訂版）

更新日：2026-11-03
対象：このリポジトリの作業共有画面。旧版の指示書を本書で置き換える。

利用者の必須条件：簡潔表示でも、社外進行・社内進行それぞれの「工程1 → 工程2」の流れを常時表示する。簡潔化を理由に工程列を削除・折りたたみ・現在値だけへ置換しない。

追加要望：一覧の各受注で、最後に変更された項目そのものを強調し、その変更日時も小さく表示する。以下Gで、現在のデータで実現する範囲と時刻の扱いを定義する。

## 1. 依頼と完成条件

既存コードを確認し、本書の第1段階を実装・検証してください。目的は、現場で「仕事を選ぶ → 対象と注意事項を確認する → 工程を記録する → 残りの工程を確認する」という操作を短くすることです。

主対象は `public/process.html`。必要な表示関数とローカル検証用ファイルの追加は可能です。既存のAPI契約と業務判定を使い、Airtableの設定・データモデル・サーバー処理は変更しません。フレームワーク移行や新規UIライブラリの導入は不要です。

作業開始時に適用対象のAGENTS.md等とgit差分を確認し、利用者の未コミット変更を保護してください。レビュー時点では `.claude/settings.local.json` に既存の変更があります。本番公開、push、実データ操作は今回の作業に含みません。

完成条件：

- 部門別一覧を読みやすくし、従来の情報量にも戻せる。
- 対応する工程が明確な場合だけ主操作を目立たせる。
- 連絡事項や現在の状況を隠さず、誤って「仕上がり」を記録させない。
- 保存成功・保存結果不明・一覧再取得失敗を区別して知らせる。
- 各受注の一覧カードで、取得した記録のうち最新の変更項目と日時を確認できる。
- 検索・QR・画像・変更・取消・新規受注などの既存導線を維持する。

## 2. コード照合で判明した設計上の注意

旧版の曖昧な指示より、この表と後続の仕様を優先してください。

| コード上の事実 | 実装上の結論 |
|---|---|
| `VIEWS.mine` は一覧の「自工程済」の判定用。複数候補はどれかが済なら済扱い | 主ボタンの工程を `mine[0]` で機械的に決めない |
| お守箔焼印の `mine` は `finish` だが、工程は生地カット→抜き→仕上がり | このビューでは「仕上がりました」だけを主操作にしない |
| Nao・2F 小の `mine` は `finish, seal`。断裁ステッチ・プレも `finish` を使う | 部屋の完了と全体の仕上がりを混同させる言い換えをしない |
| `mineDone` は実記録だけでなく、旧名称・抜き半製品あり・最終グループでも済を返す | 記録者・時刻・個別工程の完了を捏造しない。別工程の記録入口は残す |
| `todoRooms` は閉じた受注、最終グループ、finish記録、工程タグなしでも空になる | 空配列を「全工程完了」の証拠にしない |
| `itemTags` は品名のタグ順を優先するが、品名から読めない工程タグは末尾に足す | 返された先頭を常に確実な「次工程」と断定しない |
| `tagDone` は `S.views` も参照。検索APIは `views` を返さない | 直接検索した画面で部門別判定が完全とは限らない。追加の一覧取得で補わない |
| `mineReady` の表示根拠は直前工程とは限らず、最後の記録または材料状態 | 一律に「前工程：…」へ言い換えず、「着手判断の根拠」または既存の文言を使う |
| `progressStrip` に社外・社内の工程列、材料予定、型の状況、応援先が集約されている | 簡潔・詳細の両表示で工程列と矢印を常時表示する。情報を落とさず配置と余白を整理する |
| `write` の `writing` は自動読込の抑制用で、二重送信を防ぐ排他制御ではない | 主操作を増設しただけで送信制御まで保証されたと考えない |
| `applyUnsure` は現在 `renderRooms` の末尾から呼ばれる | 描画順を変えるなら、最後に操作停止が適用されることを明示的に保証する |
| 保存成功後に `loadView` が一覧を入れ替え、対象行が消えることがある | 保存した受注IDと結果を保持してから一覧復帰する |
| `view` 読込はサーバーで `autoSheetWait` を呼び、条件によってAirtableを書き換える | 「読取確認だけ」のつもりでも本番APIを叩かない。検証は全面モックにする |

## 4. 第1段階の画面仕様

### A. 一覧に「簡潔／詳細」の表示切替を加える

作業リストの状態フィルター付近に `表示：簡潔 / 詳細` を設置する。部門別ビューでは初回を簡潔にする。ユーザーが選んだ表示は新しい専用のlocalStorageキーに保存し、既存の `process.view`、`process.mode` を転用しない。保存不能でも動作すること。

「全件」「Recent 1day」「Fax」と、品番・品名検索の結果一覧は今回の簡略化対象にせず、従来の詳しい表示を保つ。これらには簡潔切替を表示しない。部門別ビューに戻ったときは選んだ表示を復元する。

簡潔表示で残す情報：

1. 既存の状態バッジとその根拠。意味の重複する説明を繰り返さない。
2. `itemShort(o)` による品名、Book / WorkCord、`facts(o)` の数量・納期。
3. 数量・納期の「元の値」、曜日、今日・明日・超過日数など、現在の変更・期限表示。
4. 社外進行・社内進行の2列。「工程1 → 工程2 → …」を両方とも常時表示し、現在の段階を強調する。既存の過去・現在・残工程の表示、工程名、順序、矢印を維持する。現在値だけへの置換や途中工程の省略はしない。社外の取消・納期変更等も隠さない。
5. 紙入荷日の予定・確認待ち・予定日経過の情報。現在の `paperNote` と `progressStrip` の条件を維持する。
6. 抜型状況と応援先のタグ。既存の矛盾タグ抑制を維持する。
7. 連絡事項全文と画像サムネイル。

簡潔表示は情報の削除ではなく、余白・札の内側の間隔・見出し配置・重複説明を整理して高さを抑える。工程列を1行に収めるために文字を極端に小さくしたり、末尾を省略したりしない。収まらなければ順序が追えるように折り返し、社外と社内の列を混ぜない。連絡事項全文と工程列のためにカードが高くなることは許容する。詳細表示は同じ工程列をより余裕のある配置で見せる。

簡潔・詳細の工程表示は共通の `progressStrip`・`outFlow`・`inFlow` を再利用し、モードごとに工程データや材料日付・型タグの判定を作り直さない。表示モード切替の前後で工程名・順序・現在位置・残工程が一致すること。社外の過去段階は現在値から組み立てた流れであり、各段階を実測した履歴として扱わない。

カード全体から詳細を開く。カード内の誘導文は「詳細・工程を記録 →」程度の短い文字でよい。既存buttonの内部にbutton/a/detailsを入れない。画像タップは全画面表示だけを行い、工程詳細を同時に開かない。

表示切替は通信や再検索をせず、取得済みデータだけで行う。状態の件数・絞り込み・順序・選択受注は維持し、可能な範囲で先頭可視行を保つ。

### B. 詳細の情報と主操作を上部にまとめる

新しいページやモーダルにはせず、既存 `stepCard` と一覧復帰を使う。表示順は以下とする。

1. 戻る操作。
2. 保存結果不明の警告（該当時。常時見える位置）。
3. 品名全文、Book / WorkCord、数量、納期、連絡事項全文、現在の注意情報。
4. 社外進行・社内進行の工程列。操作詳細でも常時表示し、履歴の折りたたみの中だけに置かない。
5. 現在の作業ビュー名と状態、および以下Cの主操作。
6. 操作メッセージ `stepMsg`。折りたたみの外に置く。
7. 工程記録から見た残工程の案内（以下Eの条件）。工程列と同じ内容を長く重複させない。
8. 「この型を探す」「生地を照合する」の既存リンクと画像。
9. 以下Dの補助操作。

連絡事項全文を主操作より前で読めるようにする。主ボタンを画面下へ固定しない。長文時に注意事項を読み飛ばして押す構造を避ける。

主ボタンのラベルは原則として既存の `s.label` を使い、付近に「押すと完了を記録します」と表示する。特に `finish` は「仕上がりました」のままにする。「プレ完了」「Nao完了」等へ言い換えて送信内容を隠さない。

### C. 主操作の選択規則を固定する

これは表示優先度の規則であり、工程を記録できるかどうかの新しい業務判定ではない。送信は既存の `chooseStep → doComplete → write` を通す。

| 開いた場所・状態 | 上部に表示する操作 |
|---|---|
| CAD | `cad` |
| オートン抜き | `o` |
| 機械貼 | `kikai` |
| 手貼り | `tebari` |
| たおし抜き | `tk`/`tm` のvariant.tagと `工程(自動)` の対応が片方だけならその工程。両方またはどちらも該当しなければ、同じ強さの2候補として表示 |
| 2F 小、Nao | 未記録の `seal` と `finish` を同じ強さの選択肢として表示。自動でどちらかを選ばない |
| お守箔焼印 | 「工程を選んで記録」から工程一覧を開く。生地カット・抜き・仕上がりの順を独自推測して主ボタンにしない |
| 断裁ステッチ、プレ | 「工程を選んで記録」から工程一覧を開く。部屋専用の完了記録と誤認させない |
| 全件、Recent、Fax、品番・品名検索 | 「工程を選んで記録」。前に見ていた `S.view` を流用しない |
| 上記以外のビュー、必要な定義不足 | 「工程を選んで記録」。安全にフォールバックする |

優先適用する例外：

- `o.closed` の場合は自動選択した完了主ボタンを出さず、閉じた状態を表示する。既存の工程一覧への入口と、サーバーが許可する操作は維持する。
- `mineDone(o, v)` が成立する場合は、上部に既存の「済」の根拠を表示する。記録日時は実際の記録がある場合だけ表示する。元の根拠が「抜き半製品あり」「仕上がり済」ならそのまま示す。
- 「自工程済」でも別の工程記録が必要なことがあるため、「他の工程を記録」への1操作の入口を残す。
- 待ち・状態未確認でも既存で可能な記録操作を禁止しない。理由を主操作の直前に表示し、「着手推奨」の表現にはしない。
- タグ一致を調べるための別の品名パーサーを作らない。`hasTag` とAPIのvariant.tagを使う。
- 現時点の1工程1variantを前提に決め打ちせず、複数variantなら既存の選択処理を使う。

### D. 補助操作の開閉は1段だけにする

以下のまとまりで展開式にする。入れ子の折りたたみは作らない。

| 見出し | 内容・初期状態 |
|---|---|
| その他の工程を記録 | 未記録の工程一覧。主操作が確定している場合は閉。上部が「工程を選んで記録」の場合は同ボタンで開き、スクロール・フォーカスを移す |
| 材料・在庫の状況を記録 | 既存の状況工程と3つの社外状態ボタン。材料待ちのときは開、それ以外は閉 |
| 数量・納期・紙入荷日を変更 | 既存Editorを使用。初期は閉。伝票発行後の制限・案内を維持 |
| 応援先 | Room操作。現在の指定先をsummary付近にも表示。初期は閉 |
| 進行と完了記録 | 工程の記録者・日時、既存の取消操作。初期は閉。工程列そのものは詳細上部で常時表示し、ここだけに隠さない |
| この品目で新規受注 | 既存の入口ボタンを残す。すでに開閉式なので外側にもう1段追加しない |

削除は既存の表示条件を満たすときだけ、新規受注とは別の位置に置く。目立つ主操作にしない。

同一の未完了工程ボタンを上部と補助領域に二重表示しない。主操作に出した工程は補助一覧から除外し、すべての既存工程に到達できることを確認する。済の表示と取消を押せる完了ボタンに戻さない。

同じ受注の再描画では開閉状態を保ち、別受注を開いたら初期状態に戻す。開閉だけでEditorや新規受注フォームを再生成して入力を消さない。既存の「やめる」や保存確定時のフォーム再生成は許容する。

処理中・入力エラー・結果メッセージは押した操作の近くでも分かるようにする。`stepMsg` が画面外なら、入力エラー時にメッセージへ案内するか、その入力欄の近くに同内容を示す。入力のたびに勝手にスクロールしない。

### E. 「次工程」は根拠のある範囲で表示する

第1段階では、部門別一覧から開き、工程の判定に必要な `S.views`・`S.steps` が揃っている受注に限って、新しい残工程案内を出す。検索から直接開いた場合は追加のAPI取得をせず、「上部の工程列と完了記録を確認してください」とする。

既存の `itemTags`・`tagDone`・`todoRooms` の判定を再利用する。ただし以下を区別する小さな表示関数を用意する。

- 品名由来の認識済みタグで全工程の並びを説明でき、各工程の完了判定にも対応している場合：
  - 「工程記録から見た残り：A → B」
  - 先頭を示すなら「次の工程候補：A」。これから着手可能になったという保証や通知完了の意味を持たせない。
- `itemTags` が末尾に補った工程、未対応タグ、判定に必要な定義不足などがある場合：
  - 順序を断定する矢印や「次」の強調を使わない。
  - 「工程候補：A・B（順番・完了状況を確認）」程度にとどめる。
- タグがない、候補を特定できない場合：
  - 「次工程を確認してください」。
- 残工程が空の場合：
  - 実際の `finish` 記録または現在の `progIn=仕上がりました` があれば「仕上がりの記録があります」。
  - `group=最終` だけなら「現在は仕上がり済の扱いです」。
  - 閉じた受注ならその社外状態を表示する。
  - それ以外は「表示できる残工程はありません。必要な作業を確認してください」。

`ITEM_TAG` の対応を別の場所に複製しない。品名タグ由来かどうかの情報が必要なら小さな共通パーサーに切り出すが、既存 `itemTags` の結果・順序が変わらないことをテストする。担当不明の工程を勝手に完了扱いにしない。

主操作前に表示する残工程には現在の自工程も含まれ得る。「引き継ぎ先」と呼ぶのは避ける。Roomの応援先は残工程とは別に扱う。作業者の割当、通知、置き場所は今回追加しない。

### F. 保存後の案内を見失わせない

工程完了の成功を `outcomeUnknown` 等の既存条件で確認したあと、受注ID・品名・記録した工程・更新済み受注情報を保持して一覧を取得する。

- 一覧再取得に成功し同じIDがある場合：再取得した受注を残工程の表示に使う。
- 一覧再取得に成功し対象がなくなった場合：保存応答を反映した情報で表示する。最新の受注全体を再取得したと偽らず、候補表示にとどめる。
- 保存は成功したが一覧再取得に失敗した場合：「完了記録は保存済み／一覧の更新に失敗」と明示する。再試行は一覧更新だけ。工程完了を再送しない。次工程の断定は避ける。
- 保存結果不明の場合：成功や引き継ぎの案内を出さず、既存の確認手順へ進む。

既存 `backToRow` の行への復帰・強調と、フィルターから外れた場合／ビューから消えた場合の説明を維持する。結果は一覧上部だけでなく、復帰した位置から見える領域にも表示する。たとえば一覧画面にだけ出る非モーダルの結果通知を用意し、対象の品番・工程と残工程を示す。

通知は自動で数秒後に消さず、閉じる操作または次の利用者操作（受注選択・ビュー変更・検索・次の書込）まで残す。自動更新で消さない。画面を大きく覆わず、必要なら下部の余白を確保する。`role=status` 等を用い、同じ内容を複数のlive領域で同時に読み上げさせない。

### G. 一覧の最新変更項目と時刻を表示する

各受注カードの中で、記録から分かる最新の変更項目を強調する。画面全体で最新の1件を選ぶ機能ではなく、受注ごとの表示とする。簡潔・詳細の両表示、全件・Recent・Faxにも適用する。検索結果一覧にも同じ表示関数を再利用してよい。並び順は変更しない。

表示例（架空データ）：

```text
数量 1,200 〈更新〉
            11/3 14:32

社内：工程表発行済 → オートン抜き完了〈更新〉 → 機械貼
                       11/3 14:32
```

変更された数量・納期・工程札など、その項目の位置に「更新」の小さな印、やや太い文字等を付け、日時を隣または直下に置く。カード全体だけを強調して変更箇所を曖昧にしない。既存の「元の数量」「元の納期」も残す。

時刻は日本時間で `M/D HH:mm` を基本にし、異なる年は年も付ける。12px程度を目安とし、薄すぎる文字にしない。マウスを乗せたときのtitleだけに隠さない。日付を省いて、昨日の更新が今日の更新に見える表示にしない。

状態の緑・青・黄土・赤、選択中の枠とは区別し、現在の進行を示す強調も維持する。点滅・自動スクロールは不要。「更新」は既読・未読や「数分以内」という意味にはせず、取得できた最新記録を示す。再描画・画像取得・モード切替で時刻や強調対象を変えない。新しい記録が取得されたら、その項目へ強調を移す。

#### G-1. 既存データで実装する対象

`api/_process.js` の `describe` と一覧フィールドを確認済み。現在のレスポンスから取得できる候補は以下。

| 候補 | 日時の根拠 | 強調する位置 |
|---|---|---|
| 各工程・状況の完了記録 | `o.done[step.key]` の記録文字列 | 対応する社内工程札 |
| 数量変更 | `o.amountLog` の最終行末尾にある操作日時 | 現在の数量 |
| 納期変更 | `o.ndateLog` の最終行末尾にある操作日時 | 現在の納期 |
| 工程表発行 | `o.printedAt` | 工程表発行済の札 |

候補を共通関数で抽出し、有効な日時の最大値を選ぶ。`latestKey` は現在の進行を優先するため、この用途の最新変更選択にそのまま使わない。

数量・納期のログは `旧値→新値 氏名 YYYY-MM-DD HH:mm`。納期の旧値や新値を操作日時と誤認せず、末尾の日時を厳密に読む。現在の値がログの変更後の値と一致しない場合、そのログを現在値の変更日時として付けない。

タイムゾーンなしの既存記録は日本時間として扱い、端末のタイムゾーンに依存させない。時刻付きISO形式はオフセットを尊重する。日付だけ・不正な日時には架空の `00:00` や現在時刻を補わない。

記録精度が分単位なので、複数の項目が同じ最大日時になる場合は、勝手に前後を決めず、その項目すべてを強調して「同時刻の記録」と分かるようにする。

#### G-2. 「受注全体の最終変更」との違いを明示する

現在の一覧APIには、社外進行・紙入荷日・Room・連絡事項・型状況等の変更日時を統一して返す情報がない。工程取消の時刻も残存する `done` の記録だけからは分からない。したがって、G-1だけで受注全体の最終変更を保証しない。

一覧の凡例に「更新：取得できた記録のうち最新」を表示する。全項目の履歴を取得するまでは「受注の最終更新」「最後に変更されたのは必ずこの項目」といった断定をしない。有効な候補がない受注には強調も架空の時刻も付けない。

以下は更新日時として使用禁止：`S.listAt`、`cachedAt`、一覧を開いた時刻、差分を発見した時刻、ローカル保存時刻、画像URLの変化。比較前のデータがない初回表示で、すべてを変更済みにしない。保存結果不明の操作は候補に追加しない。

数量・納期・完了の保存が確定した場合は、返された `line`・`stamp` を使う。クライアントの現在時刻を変更日時として補わない。

全項目対応に拡張する際は、既存の `TableWorkLog` の操作と受注IDに対応する日時、およびAirtable直接編集・外部システム・Automationの変更が記録される範囲を確認する必要がある。レコード単位の「最終更新」時刻だけでは変更項目を特定できない。今回のUI実装ではAPIやスキーマを推測で増設せず、完了報告に取得できない対象と必要な追加対応を記載する。

## 5. 操作停止と非同期処理の必須条件

新しいUIの主ボタンだけが既存の停止処理から漏れることを防いでください。

- 共通の操作状態反映関数または明示的なdata属性を使い、描画後にも状態を適用する。CSSクラスだけに依存する既存セレクターは変更箇所ごとに点検する。
- 書込開始から応答反映まで、同じ詳細の別の書込を重ねない。主操作・取消・材料・Room・Editor保存・新規受注・削除を対象にする。
- 新規受注の重複確認後の `force` 再送は既存仕様の明示的な例外として維持する。ネットワーク失敗の自動再送は加えない。
- DOM上のdisabledだけでなく、実行直前に受注IDと書込中・結果不明を確認する。対象は開いている受注ではなく操作開始時のIDで保持する。
- 処理中に対象や画面を変える戻る・候補前後・ビュー切替・検索等は一時的に抑止するか、世代番号等で古い応答を新画面に適用しない。実装方法は一貫させる。
- 処理後にすべてのbuttonを無条件に有効化しない。材料の変更禁止、`amountLocked`、結果不明等の既存条件を再適用する。
- `applyUnsure` を描画の最後に適用する。主操作、開いているEditorの保存、補助領域の書込も漏らさない。「記録の状態を確認」と読取・戻るの導線は残す。
- 新規受注・削除には専用の結果不明メッセージがある。元受注の `S.unsure` 確認で新規作成・削除結果も確定できると扱わない。既存の「探し直して確認」の案内を維持する。
- `canAutoLoad`、`listGen`、`listBusy`、`rowsSig`、画像の遅延取得を維持する。画像到着は詳細全体を再描画しない。
- 個別Editorの業務ルール、認証・取消権限・APIの競合応答は変更しない。

ここはUI再配置に直接関係する範囲の修正です。既存の認証やバックエンド全体の改修へ広げないでください。

## 6. 維持する既存機能

- 部門別ビュー、全件、Recent、Fax、状態フィルターと件数。
- 通常一覧の着手可→待ち等→済、各群内の納期順、RecentのkeepOrder。
- 最終閲覧ビュー・モード保存、URLの `?view=`、`?book=&wc=`、QR読取。
- 品名2キーワード検索、アーカイブを含む検索、前後の候補移動。
- 新規受注の `pinNew`、`newIds`、「今作成」の表示、作成後の検索モードへの移動。
- 元数量・元納期、材料予定、連絡事項、型の状況、応援先。
- 工程完了・取消・材料在庫記録の元の値と実績集計。
- 伝票発行後の編集制限、数量の確認・制限、過去日確認、紙入荷日の削除。
- 「この型を探す」「生地を照合する」、画像の複数枚・拡大・原寸・期限切れ案内。
- 明示的な更新・失敗時の再読込・情報の時刻表示。
- 戻る、選択行への復帰、画面上部の固定見出しとスマホのスクロール補正。
- dark/light/vivant/shelfの4テーマと、着手可＝緑・済＝青・待ち＝黄土・注意＝赤の意味。

画面は360px・390px程度とPC幅で確認し、全体の横スクロールをなくす。主操作は高さ48px以上を目安にする。画像列の既存の横送りは維持してよい。長文・改行・数量未設定・納期未設定にも対応し、状態は色と文字で伝える。入力値の表示にはtextContent等の安全なDOM構築を使う。

## 7. 実装・検証の進め方

1. 現在の差分と対象関数を読み、既存回帰テストを実行する。
2. 上部主操作・候補表示を小さな関数で実装し、判定が曖昧なケースを先に検証する。
3. 一覧の簡潔/詳細切替、詳細の情報配置、補助操作の整理を行う。
4. 完了後の案内と操作停止を接続する。
5. 全面モックのブラウザ確認と回帰テストを行い、差分をレビューする。

レビュー時の基準：`node tools/process-regression.cjs` は20/20成功。Claude Code自身も変更前後に実行すること。既存テストにはページから関数を抽出するものがあるため、正当な関数分割でハーネスを変える場合は、同じ挙動検証を維持する。テストを無効化して通さない。

モック検証では `/api/session` を含む認証、`/api/airtable-update-progress` のすべてのactionを差し替える。未モックのAPI要求は失敗させ、本番へフォールバックさせない。作業一覧読込にも書込の副作用があるため、本番への「読取だけの確認」も実施しない。必要なら静的なローカルサーバーとテスト用画像を使用する。実PAT・社員PIN・顧客データは不要。

### 必須の確認シナリオ

| ケース | 合格条件 |
|---|---|
| 機械貼・未記録 | 主操作が機械貼完了。送信のstep/variant/idは従来と一致 |
| たおしKのみ/Mのみ/両方/なし | 片方のみ確定。両方・なしで勝手な自動選択をしない |
| お守箔焼印・未記録 | 仕上がりだけを主ボタンにしない。生地カット・抜きへ到達できる |
| Nao・2F 小 | seal/finishを混同せず、片方の記録後も他工程への入口がある |
| 抜き半製品あり・旧手貼り名・最終グループ | 既存どおり自工程済。個別の記録者を捏造しない |
| 直接URL検索と、一覧を見た後の検索 | 前のビューにより主操作が変わらない。定義不足で次工程を断定しない |
| 材料待ち・予定日経過・取消・型修正・応援・長文メモ | 簡潔一覧でも必要な情報が見える。詳細で全文・全進行へ到達できる |
| 簡潔/詳細の表示切替、操作詳細を開く | いずれも社外・社内の工程列と矢印が常時見える。モード切替で工程が欠けず、順序・現在位置が変わらない |
| 数量・納期・工程の記録日時が異なる | 各受注で最新の有効記録の項目だけを強調し、その日時を小さく表示 |
| 同時刻の複数変更、記録なし、不正日時、現在値とログの不一致 | 同時刻は複数表示。根拠のない強調・架空の日時・誤った最終更新の断定をしない |
| 日付を含む納期変更ログ、日付境界、端末の別タイムゾーン | 変更日時と納期を混同せず、日本時間で表示 |
| 再読込・画像差替え・表示切替・保存結果不明 | 読込時刻で更新を偽らず、既存の工程列と状態色を維持 |
| 全件・Recent・Fax・検索 | 従来の情報量と並びを維持 |
| 品名タグ #o#nao#ki、工程(自動)の順は異なる | 品名由来の順を維持 |
| 未対応タグ・タグなし・closed・finish | 空配列だけで全作業完了を表示しない |
| 完了成功後、同じ行/フィルター外/ビュー外 | 成功結果と対象が見え、復帰処理が破綻しない |
| 完了成功、一覧再取得失敗 | 保存済みと更新失敗を両方示し、completeを再送しない |
| 他者の先行完了・結果不明・状態確認も失敗 | 成功を捏造せず、操作停止と確認導線を維持 |
| 連打・Enter・材料保存中の完了・描画後のボタン | 二重書込や、禁止ボタンの意図しない再有効化がない |
| 入力中の折りたたみ、画像の遅着、一覧自動更新 | 入力が消えず、勝手な対象変更がない |
| 新規受注・重複確認・削除・結果不明 | 元の条件・案内・新規行表示を維持 |
| 4テーマ、360/390px、PC、キーボード | ラベルと状態が読め、操作・フォーカス・画像表示が成立 |

新規テストは主操作選択、工程順の確実性、保存と再取得の成否分離、二重操作防止などの挙動に絞る。CSS値やDOMの細部を写すだけのテストは不要。画面確認を実行できなかった場合は、未確認の端末・ケースと理由を報告する。

## 8. 今回は設計メモだけに残す第2段階

- 本人の担当工程登録と個人ホーム。現状は「最終閲覧ビュー」であり、社員の所属情報ではない。
- 前回閲覧後の変更バッジ。既読の単位・保管場所を決めてから実装する。
- 最新変更の全項目対応。第1段階Gの既存記録による表示を土台に、社外進行・Room・紙入荷日・取消・直接編集等の変更元と日時の取得を設計する。既読/未読管理とは別の機能として扱う。
- 待ち原因別の横断表示、滞留時間。待ち始めた時刻を現在の状態から推測しない。
- 置き場所、申し送り、通知、作業者割当。
- 工程順や工程ごとの完了が構造化されたデータによる確実な引き継ぎ。
