## 2. 今回再現した修正候補

### P1：削除の途中に完了記録が入っても、その受注を削除できる

対象：`api/_process.js` の `deleteOrder`（819行以降）、条件判定（845行付近）、台帳作成とDELETE（861行以降）。

再現した順序：

1. 削除APIが受注を取得し、工程記録がないことを確認する。
2. 削除台帳を作成する処理の途中に、別操作の `complete` を実行する。
3. 完了APIが成功し、受注に機械貼完了記録が保存される。
4. 元の削除APIはそのままDELETEを実行し、成功を返す。

モックで、DELETE直前には完了記録が存在し、削除APIの応答は `200 / ok:true`、処理後の受注は不存在となった。

対応方針：削除と工程記録などの更新を、受注単位で複数端末・複数サーバーから調整できる仕組みにする。Excel等の書込経路も含める。画面のボタン停止やサーバー内の一時的なMapだけでは足りず、削除直前の再読込だけでも競合する時間が残る。

### P1：削除結果を確認できない場合に「受注は残っている」と断定する

対象：`api/_process.js:883` 付近。

再現した順序：

1. 偽Airtable側ではDELETEを反映し、応答だけ通信例外にする。
2. 続く受注のGETにも通信例外を返す。
3. APIは `502 / ok:false` とし、台帳を「要確認」にする。
4. 実際には受注がないのに、処理メモへ「受注は残っている」と書く。

対応方針：「存在を確認」「不存在を確認」「確認不能」を分ける。確認不能は同じ要求IDを保ったまま照合し、表示と台帳の両方で結果不明として扱う。事務所側が「要確認」をどう扱うかは、このリポジトリだけでは確認できない。

### P2：棚登録でAirtable更新に失敗しても、登録完了として入力を消す

対象：`public/scan-register.html` の `submitUpdate`（528行以降）、587〜596行付近。

現設定は `AIRTABLE_ENABLED=false`、`PROGRESS_ENABLED=true`。Google Sheets保存の後に、進行更新APIの `stored` でAirtable側の抜型状況・Location・LastSeenを更新する。

実関数をVMに抽出し、Sheetsを成功、進行更新を `ok:false` にすると、次の結果になった。

- 画面通知は「登録完了！ 1件を保存しました」。
- Airtable側の失敗は `console.warn` のみ。
- 型の選択は0件になり、固定棚も解除される。

対応方針：「棚の保存済み／作業共有への反映失敗」を分けて表示し、未反映の品番と棚を保持する。成功したSheetsへの再送を含め、各処理を安全に再確認・再実行できる契約を先に決める。`stored` は実績記録にも関係するため、単純な自動再送を追加するだけにはしない。

## 3. 便利になる機能案

規模は現構成からの相対的な目安。事務所PC側の変更や運用調整は別途必要。

| 優先度 | 機能 | 現場でできるようになること | 規模 |
|---|---|---|---|
| 1 | 今日の確認 | 納期超過、今日・明日の納期、今日の路線集荷、材料予定日経過をまとめて開く | 小〜中 |
| 2 | 前回確認後の変更 | 前に確認した数量・納期等との差を見て、変更を確認したことを残す | 中。部門共有は大 |
| 3 | 連携状況の一覧 | 棚登録の一部失敗、印刷待ち・失敗、削除のExcel反映待ち等を一か所で確認する | 中〜大 |
| 4 | 引継ぎと現物の置き場 | 「機械貼へ、2階入口の台車、残り300枚」のような情報と受取確認を残す | 中〜大 |
| 5 | 型の持出・返却と棚卸 | 保管棚に加え、今どこで誰が使っているか、棚の中身が登録と合うか確認する | 中〜大 |
| 6 | 着手・中断・残数 | 完了する前の仕事について、作業中・中断理由・残数量を共有する | 大 |
| 7 | 過去受注の検索強化 | 期間・顧客・完了状態を指定して絞り込み、上限を超えた過去分を追加取得する | 中 |
| 8 | 照合結果の保存 | 撮影画像・判定・人の確認を受注から見返し、再確認や問合せに使う | 中〜大 |

### 1：今日の確認から始める

最初は「現在選んでいる作業リスト」の取得済みデータから、次の入口を作る。

- 「納期を過ぎた仕事」
- 「今日・明日が納期の仕事」
- 「今日集荷する路線便」
- 「材料の予定日を過ぎた仕事」

カードを押すと対象受注だけを表示し、件数と抽出理由を示す。個別カードには既存の社外・社内の工程列を残す。材料予定日の経過は、その時点の進行状態も併記し、実物の未入荷を断定しない。

これなら既存の `facts`、`rosenPickup`、`paperNote`、状態判定を使える。新しい判定を別実装で増やすより、既存関数から条件と説明を共通に取り出す。

部門の保存は「この端末でよく使う部門」とし、最後に見たビューから社員の担当部門を推定しない。全社向けの件数表示に広げる段階では、一覧の取得上限や部門間の重複を処理する必要がある。

### 2：「最新の更新」と「前回確認との差」を分ける

現在の `latestChanges` は、取得できた工程記録、数量・納期変更記録、工程表発行日時のうち最新を示す。未読を表す機能ではなく、連絡事項・Room・紙入荷日等すべての変更日時を網羅してもいない。

最初の追加は、社員IDと受注IDを単位に、明示的に確認した時点の値を保存して比較する方法が考えられる。

表示例：`数量 1,000 → 1,200 ／ 納期 11/12 → 11/13`。

端末保存だけなら「この端末で前回確認した内容との差」と明示する。途中で起きて元に戻った変更までは検出できない。複数端末・部門で確認を共有する場合や変更時刻を正確に出す場合には、構造化した変更イベントと確認記録をサーバー側に保存する。画面を開いただけで自動的に確認済みにしない。

### 3：連携状況は、各保存先の確認を表示する

コピー印刷と削除台帳には、すでに状態確認の土台がある。これに棚登録の部分成功を加え、「確認が必要な連携」を一覧化する。

新規受注のExcel反映も表示対象にするなら、事務所PCが実際にExcel保存を完了したことを記録する項目が必要。待ち時間やスマホ側の成功応答だけからExcel反映済みと推定しない。PC停止も検出するなら、最終稼働時刻をPC側が送る仕組みを追加する。

### 4〜6：実績と、現物の動きを別々に記録する

現状のRoomは応援先であり、作業者本人や現物の置き場ではない。引継ぎには、受注ID、送り先、置き場、数量、申し送り、送付者・受取者・日時などを持たせる。

工程順が曖昧な場合に次の部門を自動決定しない。候補を提示し、送り先を人が選ぶ。完了記録・引渡し・受取りはそれぞれ別の操作として扱う。

型の保管棚と一時的な使用場所も分ける。同じBook／WorkCordの型が複数ある運用なら、個体別の型IDも必要になる。棚卸では棚QRから登録上の中身を出し、実際に読めた型との差を確認する。

着手・中断・残数は新しい作業状態として追加し、現在の「工程完了」やインセンティブ件数にそのまま加算しない。分納・手直し・過剰生産を含め、数量の意味を決めてから進める。

### 7〜8：既存の検索・照合を記録として活用する

「同じ品番の受注をすべて見る」は実装済みだが、検索には200件の上限がある。作業リストも1ソース当たり最大500件で、全件ビューは未アーカイブとアーカイブ済を別取得している。件数を扱う機能では、取得範囲と打切りの有無を明示する。

検索強化は期間指定と追加取得を中心にする。Bookが違えば同じWorkCordでも別品目なので、既存のBook／WorkCordの組を維持する。

照合結果を保存する場合は、対象の受注ID、参照図面の版、撮影画像、寸法条件、判定、利用モデル、人の確認を結び付ける。AIの判定と人が確認した結果を分けて表示する。保存先・閲覧者・保存期間も決める。

## 4. 推奨する順序

1. 削除の競合・結果不明、棚登録の部分成功を修正する。
2. 取得済みリストを使う「今日の確認」を追加する。
3. 「この端末で前回確認した内容との差」を追加する。
4. 各連携の確認項目を整え、連携状況をまとめる。
5. 引継ぎ・置き場・持出返却を追加し、必要に応じて着手や残数へ広げる。

最初の追加機能としては「今日の確認」を推す。既存の記録を活用でき、朝の確認や仕事を選ぶ手間を減らす効果を検証しやすい。
