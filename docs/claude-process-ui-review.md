# 作業共有画面：実装後レビューと追加修正案

レビュー日：2026-11-03（日本時間）  
対象：`2baf915` とその親 `4466976` の差分、および `claude-process-ui-implementation.md` の第1段階。

主要な表示構成は指示書に沿っている。既存の回帰テストは **32/32成功**。ただし、保存と先行する読込の競合を防ぐ処理が不足しているため、この点を修正してから次の公開に進めたい。今回のレビューではアプリ本体を変更していない。

## 1. 優先修正：保存中に先行読込が反映され、保存済みの値が画面へ反映されない（P1）

対象：`public/process.html` の `runOp`（666行付近）、`loadView`（1356行付近）、各Editorの保存処理（数量は1110行付近）。指示書5の非同期処理の条件に対する未解消事項。読込側の競合は以前から成立し得るが、今回追加した排他制御でも防げていない。

再現する順序：

1. 数量100の受注を開き、一覧の「更新」を押す。応答を保留する。
2. 更新が終わる前に、その受注の数量120を保存する。保存応答も保留する。
3. 先の一覧読込が、保存前の数量100を返す。
4. 数量保存が、成功・数量120を返す。

ページの実関数をNodeのVMへ抽出し、DOMと通信をモックしてこの順序を実行した結果：

```json
{
  "savedAmount": 120,
  "currentOrderAmount": 100,
  "displayedAmount": 100,
  "message": "仕上がり数量を 100 → 120 にしました"
}
```

`runOp` は書込同士を止めるが、開始前に発行済みの読込を無効化しない。`loadView` の `S.orders = j.rows` で受注オブジェクトが置換され、保存処理が保持する `o` が表示中の受注から切り離される。成功後の `renderSteps` は古い数量を持つ新しいオブジェクトを参照する。納期・紙入荷日・Roomでも同じ構造がある。

修正方針：

- 書込開始時に、それ以前に発行した一覧・検索・状態確認の読込世代を無効化する。
- 応答反映直前にも、読込の世代・モード・対象が有効か確認する。呼び出す時点の `busyNow()` だけでは不足する。
- 完了後に明示して行う一覧再取得は、書込前の読込と区別して反映できるようにする。単純に「`op` 中の全読込を拒否」すると、完了後の再取得まで止まってしまう。
- 必要に応じて、保存結果の反映先を操作開始時のIDで確認する。

追加テスト：先行読込→数量保存→古い読込応答→保存成功、の順で画面と成功メッセージが一致すること。納期とRoomも同じ競合を確認する。

## 2. 補助領域で工程記録に失敗すると、エラーが画面外にしか出ない（P2）

対象：`renderStepLists`（1931行付近）と `doComplete`（2175・2180・2185行付近）。指示書4-Dの、押した操作の近くで処理結果が分かる条件に未対応。

「その他の工程を記録」を開いて下部の工程を押すと、通信中・通常の拒否・他者による先行完了の案内は、詳細上部の `stepMsg` だけに出る。`doComplete` に近傍メッセージやエラー時の案内スクロールがない。長い連絡事項や工程列があると、押した位置から失敗理由を確認できない。

実関数に `{ok:false,error:'TEST_SERVER_REJECTION'}` を返すモックでは、`stepMsg` の更新だけが実行された。実際の画面外への距離は未確認。

修正方針：操作元の領域を `chooseStep` から渡し、既存の `sayAt` を再利用して近くにも結果を示す。あるいは、エラー時だけメッセージへ案内する。読み上げ用のlive領域は1か所を保つ。

追加テスト：主操作・補助の工程・variant選択からそれぞれ拒否を返し、利用者が失敗理由へ到達できること。連打の防止も維持する。

## 3. 再取得中に別受注を選ぶと、以前の保存結果通知が復活する（P2）

対象：`toastRetry` のハンドラー（2222行付近）。指示書4-Fの「次の受注選択などで結果通知を消す」という条件に未対応。

再現する順序：

1. 保存成功・一覧再取得失敗の通知で「一覧だけ読み直す」を押す。
2. 応答を待つ間に別受注を開く。この時点で `hideToast` が通知を消す。
3. 再取得が失敗する。

ハンドラーは開始時に保持した `t` を使って無条件に `showToast` するため、別受注の詳細に以前の受注の結果通知が再表示される。実ハンドラーを抽出したモックで `oldToastReappeared: true` を確認した。

修正方針：`await loadView` の後に `S.toast === t`、モード、通知の世代を確認する。閉じる・受注選択・ビュー変更・検索などで失効した通知には、成功時も失敗時も触れない。読込データ自体の反映制御は項目1と合わせて直す。

追加テスト：再取得待ち中に通知を閉じる／別受注を選ぶ／検索へ切り替える。それぞれ遅い失敗応答で通知が復活しないこと。

## 4. 不正なタイムゾーンを日時として受理する（P2）

対象：`recTime`（861行付近）。指示書4-G-1の不正日時を候補から除外する条件に未対応。

実関数で確認した例：

| 入力 | 現在の結果 | 期待する扱い |
|---|---|---|
| `2026-11-03T14:32:00+99:99` | 有効な時刻へ換算する | `null` |
| `2026-11-03T14:32:00+09:xx` | オフセットなしと判断して日本時間で受理する | `null` |

正規表現が日時の途中まででも一致し、オフセットの範囲チェックもない。不正な記録が「最新の更新」の選択へ入る可能性がある。

修正方針：氏名部分と末尾の日時部分を分け、日時部分全体が許可する形式に一致することを確認する。オフセットの時・分の範囲も検証し、壊れたオフセットを日本時間へフォールバックさせない。日本時間の既存書式と、有効なISOオフセットの両方を維持する。

ECMAScriptの日時形式・時差表現は[公式仕様](https://tc39.es/ecma262/2025/multipage/numbers-and-dates.html#sec-date-time-string-format)を参照。ただし、タイムゾーンなしの業務記録を日本時間と扱うことは本アプリ固有の要件として維持する。

## 5. 次に改善するとよい点（コードからの提案・画面では未確認）

### キーボードの復帰位置

`closeDetail` は行へ `focus()` するが、保存後の `backToRow` はスクロールのみ。詳細を非表示にし、一覧DOMも再生成するため、保存後にどこからTab操作を再開するかを明確にしたい。対象行が残る場合はその行、消えた場合は一覧の見出しなどへ移す。表示切替で押したボタン自身を再生成するケースも確認する。[W3Cのフォーカス順序の説明](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)を確認基準にできる。

### 結果通知の高さと余白

`body.has-toast .wrap` の下余白が170px固定。一方、通知は品名・失敗理由・残工程・ビューから外れた説明によって高さが変わる。360px幅、長い品名、文字拡大で通知が最終行やフォーカスを覆わないか確認し、必要なら通知の実測高に合わせて下余白とスクロール余白を変える。[W3CのFocus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)にも固定フッターによる隠れとスクロール余白の考え方がある。現段階でWCAG不適合を実測したわけではない。

### テストの組み合わせを増やす

追加されたテストは判断関数や書込ロックを単独で検証している。次は機能の追加より、読込・保存・通知を組み合わせた応答順の検証を優先したい。モックサーバーに読込側の遅延と、書込は反映されたが応答だけ失われるケースを足すと、項目1・3および結果不明からの復旧を再現しやすい。現在の `unknownWrite` はDBを書き換える前に異常応答を返すため、「実際は保存済み」の確認には不足する。

成功・待機・エラーの通知については、[W3CのStatus Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)を参考に、視覚表示と読み上げを両方確認する。
